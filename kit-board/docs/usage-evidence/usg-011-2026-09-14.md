Of the eleven shared keys, seven have a more complete companion revision and four a more complete v1 revision; none are equal in calls and tokens, because an identical republication is stored once (see below). Canonical rows from v1 sources contribute 3,962,789,770 tokens, of which 3,945,265,286 sit on keys the companion never stored at all.

Reading the v1-only keys:

- **The retired rows are not redundant.** Dropping them would remove 32,445 calls and 3.95 billion tokens (44% of the canonical total) from the dashboard. The audit's warning stands: v1 history is preserved as coarse rows, and no finer supported fact exists for those hours.
- **Almost none of them compete with companion observations.** Only 25 of 783 v1-only keys fall in an hour where the companion stored other keys for the same account, and 20 of those 25 are for the Codex account in September. Those are the only candidates for a session-identity difference between the two collectors; every other v1-only key is in an hour the companion simply has no rows for, which matches the companion's backfill pin (August 1 on the Windows host) and the transcript retention on each machine. The Claude work account has v1 rows only, because its companion binding has not published hourly buckets.
- **"No companion copy" over-counts.** The hourly ledger's unique key excludes the publishing source, so when the companion republishes a bucket byte for byte, the row is dropped as a duplicate of the v1 revision and the key still reads as v1-only. The pending-outbox classification below shows the two collectors do produce identical buckets on the Windows host. The 704 Codex and 80 Claude v1-only keys the audit counted therefore include keys the companion did observe and could not store twice; the server cannot tell those apart from keys it never observed without the local checkpoints, which is why USG-002's per-machine reconciliation (all 17 Claude and all 135 Codex Windows keys overlapping) is the stronger evidence for that host.
- **No double counting.** The canonical selection dedupes by key, so a shared key contributes one row. The 25 candidate keys carry distinct session hashes and are counted separately; reconciling them requires the transcripts, not the server.
