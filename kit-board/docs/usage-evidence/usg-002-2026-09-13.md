## Private backup and isolated restoration

A private recovery bundle was created outside the repository. Its generated manifest records every file with size and SHA-256 metadata. It includes the three scheduler definitions, companion configuration and logs, the exact pending detailed artifact, installed adapter code, publisher configuration, and WAL-safe SQLite backups for the companion and both v1 collectors.

The machine verifier copies the bundle into a temporary directory before reading it. Verification passed for 31 machine files, all three scheduler XML definitions, and all three SQLite databases. SQLite integrity checks returned `ok`; the companion database exposed 13 tables and each v1 database exposed seven. The pending-artifact digest matched the private manifest.

A logical production-database export was also captured because the deployed database credential was not available for a native dump. The export contains the six migrations actually applied to the production schema plus row data for 19 tables. A restore script created a disposable PostgreSQL 17 container, applied those migrations, imported the rows with constraints active, and compared source and restored row counts and ordered checksums. All 2,906 rows matched, and the disposable container was removed by the verifier.

## Detailed publication diagnosis

The preserved Windows Codex artifact is a 94,910-byte partial September report containing 721,650,963 tokens, 5,527 calls, and 50 threads. It passes the current local parser and remained byte-identical through nine retries. A production query found neither its idempotency key nor its content hash, so there is no uncertain successful write to reconcile before retrying.

Production request logs showed the current rejection is HTTP 401. The local publisher key is not accepted by the deployed primary report-publisher credential set. That primary environment value is stored as a non-readable hosting secret, so editing it in place would risk replacing unrelated producer keys.

The source now supports an additive `USAGE_INGEST_KEYS_JSON` credential set. It is consulted only for usage reports, preserves the primary secret unchanged, and permits a staged recovery or rotation without changing a known producer identity. No prior production report matched this Windows subject or machine label, so recovery selected a stable new producer alias and retained it in the private activation record. Focused tests cover report-kind isolation, simultaneous old/new usage keys, and invalid entries. The repository source for the detailed publisher and scheduled companion retains the numeric HTTP status and only a finite allowlist of application error messages; arbitrary, malformed, truncated, structured, or non-JSON response content is never copied into diagnostics. Those diagnostic changes passed source tests, but the isolated production release contained only the authentication files and this pass did not replace the installed Windows companion binary.

Because the active deployment contained uncommitted source behavior, a clean checkout at its Git SHA would have regressed production. The retained deployment source was reconstructed outside Git instead: all 255 source files matched their Vercel UID/SHA-1, and the candidate differed only by the modified authentication entrypoint and new credential helper. Its focused tests, typecheck, and production build passed.

The additive credential was added as a production secret. Before promotion, `{}` posted to `/api/reports` with the recovery key returned the exact parser-level `400` response `{"error":"Invalid monthly usage envelope"}`. The same candidate returned exact `401` responses for a wrong usage key and for the recovery key used against another report kind. The public production alias repeated all three results after promotion.

The live pending file matched the preserved backup hash before retry. The adapter published that exact artifact first and recorded an authenticated receipt, then published the newly analyzed current snapshot. A direct production-database check found the exact receipt once, with the intended usage kind, partial September period, and recovery producer. The current snapshot was the canonical selected report.

The configured companion task was then invoked through Windows Task Scheduler in its installed execution context. It exited `0`, accepted six token buckets and one request record with zero rejections, and published one changed detailed snapshot. Production contained all three recovered detailed revisions, and the latest was the selected September report. The next natural hourly trigger remained scheduled for 23:10 UTC; this pass did not wait for that wall-clock occurrence.

An independent Astra high-effort review found no blocking auth or activation issue. It identified an unsafe arbitrary-response diagnostic, a request-detail coverage-definition conflict, an omitted scheduled-companion diagnostic field, and a structured-error edge case. All four were corrected and their focused tests passed before activation.
